# Check permissions, not roles, and prove it

Enterprise platforms that scale authorization all converge on the same core: **a permission string named by resource and verb is the stable unit, roles are bundles of those strings, and application code checks permissions, never role names**. AWS, Google Cloud, Azure, Stripe, GitHub and GitLab differ in delimiter and storage, but not in that grammar. Fixed roles live in code or versioned config. Custom roles show up much later as database rows that combine permissions the code already defines, and they are never used to invent new ones. External policy engines (OPA, Cedar, Cerbos, SpiceDB, OpenFGA) earn their cost when a second service or language needs the same decisions, or when permissions come from a sharing graph. They do not earn it in a single Rails monolith with nine fixed roles. For payhub, this means the plan in `docs/plans/2026-09-25-ui-design.md` section 3 has the right architecture: a frozen map in code, a check in each controller, tenant scoping that returns 404, maker-checker as a domain invariant, and UI hiding only. Its weak spots are in the details. The matrix spec as written would test the hash against itself. The plan has no verification hook that catches an action nobody authorized. `payments_write` bundles three money movements under one name that will become a public contract once custom roles or restricted API keys ship. And the permission map has no descriptions to generate docs or a TypeScript type from. The verdict at the end lists what to keep, what to change, and what to defer, with the trigger that would reopen each deferred item.

## Every major platform names permissions as namespace, resource, verb

The grammar is the same everywhere, and only the punctuation varies. AWS writes `service:Action` (`s3:GetObject`) ([AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_action.html)). Google Cloud writes `service.resource.verb` (`compute.instances.stop`) ([GCP](https://docs.cloud.google.com/iam/docs/roles-overview)). Azure writes `Microsoft.Storage/storageAccounts/.../read` and maps the verb straight onto HTTP: read for GET, write for PUT/PATCH, delete for DELETE, and `action` for custom POSTs such as a VM restart ([Azure](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions)). Stripe's restricted keys give each resource None, Read or Write, and **"write permissions imply read permissions"** ([Stripe](https://docs.stripe.com/keys/restricted-api-keys)). GitLab is the closest Rails analogue. Its abilities are `verb_resource` symbols such as `read_vulnerability`, `admin_merge_request` and `approve_merge_request`, and each default role is a YAML file listing them, with `inherits_from: [reporter]` ([GitLab developer.yml](https://gitlab.com/gitlab-org/gitlab/-/raw/master/config/authz/roles/developer.yml)). Mastodon keeps about 23 admin permissions as a frozen hash of bit flags on `UserRole` ([Mastodon](https://github.com/mastodon/mastodon/blob/main/app/models/user_role.rb)). Payhub's frozen hash is therefore a well-precedented design, not a shortcut.

Three details in these schemes matter more than the delimiter. First, **wildcards grant the future**. Azure's Contributor role holds `Actions: ["*"]`, which "includes actions defined in the future", and Azure had to add a separate `DataActions` namespace so that existing `*` grants would not suddenly reach data ([Azure](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions)). Payhub's operator admin, which deliberately lacks `proposals_decide`, shows why the admin role should list its permissions explicitly and why a new permission should start out granted to nobody. Second, **the power to manage roles is itself a privileged permission**. Azure flags any role that can write role assignments as privileged. At Stripe, an IAM Administrator "can't do anything beyond access management", and only a Super Administrator can grant Super Administrator ([Stripe roles](https://docs.stripe.com/get-started/account/teams/roles)). Payhub's `team_manage`, together with its rule that admins can only assign roles up to Admin, follows that pattern. Third, **granularity follows risk**. Stripe ships narrow built-in roles such as `refund_analyst` and `dispute_analyst` instead of a generic "write" role ([Stripe roles](https://docs.stripe.com/get-started/account/teams/roles)). Oso recommends keeping the low-level actions the code enforces separate from the higher-level permissions users assign, so that implementation details are not exposed through role configuration ([Oso custom roles](https://www.osohq.com/docs/develop/policies/patterns/custom-roles)). Once customers can compose permissions, the names become a public API, and renaming or splitting one means migrating every custom role ([Oso Academy](https://www.osohq.com/academy/what-is-rbac)). So the time to split `payments_write` into capture, cancel and refund is before anything outside the codebase refers to it.

## Fixed roles live in code; custom roles arrive late, layered on a base role

The storage split is consistent across the industry. Built-in roles ship with the product, and custom roles are tenant data. Even Oso, which sells an authorization service, says that for standard roles "a simple dictionary from role name to a string list of permissions" is enough, and that the map only has to become dynamic for custom roles ([Oso Academy](https://www.osohq.com/academy/what-is-rbac)). When custom roles do arrive, the database only combines permissions the code declares. In Oso's pattern, custom roles can only reference the permission vocabulary declared in the policy ([Oso custom roles](https://www.osohq.com/docs/develop/policies/patterns/custom-roles)). GitLab stores a `member_roles` row with a `base_access_level` plus permission flags. Each ability is a YAML file in `ee/config/custom_abilities/`, and at boot GitLab generates policy conditions from those files "without manual code changes" ([GitLab dev docs](https://docs.gitlab.com/development/permissions/custom_roles/)).

The migrations that avoided breaking existing users followed the same recipe. The existing fixed roles become immutable built-in roles with stable IDs. Enforcement switches from role checks to permission checks, which changes no behaviour because each role expands to the permissions it already had. Only then can tenants build roles. GitHub makes a custom role inherit a base role ("Read, Triage, Write, or Maintain") and "layer on additional permissions" ([GitHub](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/about-custom-repository-roles)). GCP instead lets tenants copy a predefined role as a template ([GCP](https://docs.cloud.google.com/iam/docs/understanding-custom-roles)). Inheriting a base role is the better choice because of **drift**, the main cost of custom roles. GCP says plainly that custom roles do not pick up new permissions and that the customer is "responsible for maintaining custom roles" ([GCP](https://docs.cloud.google.com/iam/docs/understanding-custom-roles)). A role that inherits its base keeps up with it automatically. The vendors also cap how many custom roles a tenant can create: 10 per GitLab group ([GitLab](https://docs.gitlab.com/user/custom_roles/)), 20 per GitHub Enterprise organization, 300 per GCP project and 5,000 per Azure tenant.

The more useful lesson is that the leaders delayed custom roles for years and kept adding *predefined* roles instead. GitHub shipped custom repository roles in 2021 and custom organization roles in 2023 with about ten permissions, then added a predefined "CI/CD Admin" role in 2024 precisely so owners would not have to maintain a custom one ([GitHub changelog](https://github.blog/changelog/2024-09-25-introducing-ci-cd-admin-a-new-pre-defined-organization-role-for-github-actions/)). Stripe's Dashboard still offers a fixed catalogue of about 25 job-function roles and no role builder ([Stripe roles](https://docs.stripe.com/get-started/account/teams/roles)). Its customer-composable permissions exist only on restricted API keys, which are "drop-in replacements for secret API keys" and come with a migration playbook built on request logs and 403s that name the missing permission ([Stripe RAK](https://docs.stripe.com/keys/restricted-api-keys)). That model fits payhub's `/v1` Bearer keys, which today carry full merchant power. If merchants ever ask for scoped keys, the same permission catalogue should drive them, which is another reason to name permissions by resource and verb now.

## Policy engines solve a multi-service problem payhub does not have

The engines fall into two families ([Zanzibar](https://www.usenix.org/conference/atc19/presentation/pang); [SpiceDB](https://github.com/authzed/spicedb); [Cerbos](https://www.cerbos.dev/news/stateless-externalized-authorization-for-scalable-applications)). **Stateless evaluators** (OPA/Rego, Cedar with Amazon Verified Permissions, Cerbos, Casbin) evaluate rules over attributes the caller supplies. They run embedded or as a sidecar, and getting data to them is your problem. **Zanzibar-style relationship stores** (SpiceDB, OpenFGA/Auth0 FGA, Airbnb's Himeji, Carta's AuthZ) are central, stateful services that answer "what can this user see" across a graph. The price is the dual-write problem: authorization data lives in two stores that cannot share a transaction, so failures cause false denials or, worse, false grants. Mitigations range from nightly full reconciliation, where discrepancies can last hours, to transactional outboxes ([AuthZed](https://authzed.com/blog/the-dual-write-problem-in-spicedb-a-deep-dive-from-google-and-canva-experience)). They also need consistency tokens (zookies or ZedTokens) to avoid the "new enemy" problem, where a permission change and a content change are applied out of order ([AuthZed](https://authzed.com/docs/spicedb/concepts/consistency)). Cedar is the most analyzable policy language, and its authors report it runs 42 to 60 times faster than Rego on their own benchmarks ([Cedar paper](https://arxiv.org/pdf/2403.04651)). But no independent head-to-head benchmark exists, and none of these engines addresses a problem payhub has.

The company case studies show what actually triggers a move. **It is decomposition, not load.** Carta started building AuthZ in mid-2019 when it began breaking up its monolith ([Carta](https://medium.com/building-carta/authz-cartas-highly-scalable-permissions-system-782a7f2c840f)). Airbnb built Himeji during its move to a service-oriented architecture ([Airbnb](https://medium.com/airbnb-engineering/himeji-a-scalable-centralized-system-for-authorization-at-airbnb-341664924574)). The most instructive case is Figma, which evaluated OPA, Zanzibar and Oso, **rejected all three**, and built its own JSON policy DSL with deny-overrides and small evaluators in Ruby, TypeScript and Go. It had three reasons: its `has_access?` methods had become so long that "engineers were nervous to modify them", permission checks were about **20% of database load**, and its Ruby and TypeScript copies of the logic had drifted apart and caused incidents ([Figma](https://www.figma.com/blog/how-we-rolled-out-our-own-permissions-dsl-at-figma/)). Even the vendors advise waiting. Oso says "you don't need to start there" and lists the warning signs: logic duplicated across services, policy changes slowing down deploys, and nobody able to say what an admin can do ([Oso](https://www.osohq.com/post/app-authorization-warning-signs)). None of those is true of payhub today. Every source on thresholds is qualitative, and the adoption guidance comes almost entirely from vendors with an interest in adoption, so the triggers in the verdict below are judgment calls based on these case studies, not measured cut-offs.

## Rails options trade boilerplate for a free safety net

Pundit is the default Rails choice: version 2.5.2, about 111M downloads, and plain `<Model>Policy` classes with `Scope#resolve` ([Pundit](https://github.com/varvet/pundit)). Action Policy is "Pundit, re-visited", with pre-checks, aliases, per-request result caching, failure reasons and scope matchers, and it had the most recent release of the group (0.7.7, September 2026) ([Action Policy](https://actionpolicy.evilmartians.io/)). CanCanCan's single `Ability` file is the classic scaling complaint, which even one of its maintainers acknowledges ([Rodi](https://medium.com/@coorasse/cancancan-that-scales-d4e526fced3d)). Rolify stores role assignments but makes no decisions, and its last release was in February 2023 ([RubyGems](https://rubygems.org/api/v1/gems/rolify.json)). The large Rails apps each built a central "can this user do X to Y" API and then went different ways. GitLab uses DeclarativePolicy conditions and rules generated from YAML. Discourse uses one `Guardian` object. Forem uses Pundit and discourages `if user.admin?` in its policies. 37signals uses no gem at all: Fizzy has `enum :role`, `can_administer_board?`-style predicates on the model, a global `before_action :ensure_can_access_account` with an explicit `allow_unauthorized_access` opt-out, and every lookup goes through `Current.user.boards.find` ([basecamp/fizzy](https://github.com/basecamp/fizzy)).

The decision that matters for payhub is not which gem but **whether "forgot to authorize" fails loudly**. Pundit's `after_action :verify_authorized` raises if an action never called `authorize`, and `skip_authorization` is the explicit way out. Pundit itself warns that this is "not some kind of failsafe mechanism", because the hook runs *after* the action and its side effects ([Pundit](https://github.com/varvet/pundit)). 37signals has no automatic guard and relies on convention plus an account-level `before_action`. Saeloun's 2026 guide says a plain role map "is fine when the app has a few roles and no record-level rules" ([Saeloun](https://blog.saeloun.com/2026/04/28/rails-authorization-patterns-complete-guide/)). Payhub does have record-level rules, but its plan already puts them in the state machine and services (layer 4), where a policy class would only forward the call. With nine flat roles, almost every Pundit policy would reduce to `permissions.include?(x)`, so the gem would add one class per resource and deliver, in exchange, only a verify hook that payhub can write in about ten lines. The hash decision and the gem decision are also independent, because Pundit's headless policies (`authorize :dashboard, :show?`) can read the same frozen map.

On tenant scoping, the literature agrees with the plan. Loading `Model.find(id)` and then authorizing "can leak whether a record exists", whereas `scope.find(id)` treats access across tenants as not found ([Saeloun](https://blog.saeloun.com/2026/04/28/rails-authorization-patterns-complete-guide/)). acts_as_tenant 2.0.0, released four days before this report, closed a hole that let polymorphic-tenant records be created for another tenant ([acts_as_tenant](https://github.com/ErwinM/acts_as_tenant/releases)). A gem-level default scope also works against payhub's operators, who read across merchants. Postgres row-level security (RLS) is the strongest backstop but has sharp pitfalls. `SET` leaks across pooled connections, so it must be `SET LOCAL`. Table owners and superusers bypass policies. And tests run as a superuser pass even when RLS is broken ([OWASP Multi-Tenant](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html); [pganalyze](https://pganalyze.com/blog/postgres-row-level-security-ruby-rails)). A secondary pentest source reports that BOLA/IDOR accounts for the majority of cross-tenant findings ([AppSecure](https://www.appsecure.security/blog/penetration-testing-for-multi-tenant-saas-architectures)), which supports the plan's view that tenant scoping is the layer that matters most.

## Operating it: frontend flags, independent matrices, denial logs, maker-checker

**Frontend.** OWASP ASVS 5.0 requirement 8.3.1 requires enforcement "at a trusted service layer", never in client-side JavaScript ([ASVS V8](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x17-V8-Authorization.md)), so payhub's "the Vue app never enforces anything" is correct. There are two ways to send permissions to the client. The first is a global list from `/me` (CASL packs its rules this way ([CASL](https://casl.js.org/v4/en/api/casl-ability-extra/))), which suits navigation. The second is per-resource flags. GitHub, for example, attaches a `permissions` object to each repository it returns ([GitHub REST](https://docs.github.com/en/rest/repos/repos#get-a-repository)), and this carries decisions that depend on the record's state or ownership. Payhub needs both. `permissions[]` can say that Support may refund, but only the server knows that *this* payment is `unknown` and cannot be refunded. Without a `can_refund` flag on the payment payload, the UI renders a button that returns 409. Figma's drift incidents show why the client's copy has to be generated from the server's source ([Figma](https://www.figma.com/blog/how-we-rolled-out-our-own-permissions-dsl-at-figma/)). ASVS 8.3.2 requires changes to authorization inputs to take effect immediately, so the client must refetch `/me` after a role change, and the server must read the role on every request rather than caching it in the session.

**Testing.** GitLab's guidelines are the best-documented model. Each permission gets a `where(:current_user, :allowed)` table that covers *every* role, because "explicit `false` values are as important as `true` values because they document the intended access boundary" ([GitLab testing](https://docs.gitlab.com/development/permissions/testing_guidelines)). A subtlety applies directly to payhub. If the matrix spec is generated from `Permissions::MERCHANT`, it checks the hash against itself and passes whatever the hash says. The expected values must come from an independent, reviewed source, such as a committed matrix file that shows every change as a readable diff. The plan also claims "a new endpoint without a permission fails CI", but that needs a separate check: list the routes and fail if any Web controller action has neither a declared permission nor an explicit public opt-out. Cross-tenant tests should use two merchants, and in payhub also a live merchant and its test twin, and they should run under the same database role the app uses ([OWASP Multi-Tenant](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)).

**Auditing denials.** OWASP lists authorization failures among the events to "always log". Each record should cover when, where, who and what, and should never include tokens, session IDs or cardholder data ([OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). The 2021 Top 10 entry for broken access control (A01) says to "log access control failures, alert admins when appropriate (e.g., repeated failures)" and to rate-limit ([OWASP A01](https://top10.owasp.org/2021/A01_2021-Broken_Access_Control)). The multi-tenant cheat sheet adds "server-verified tenant context" to each event and says to watch denials for cross-tenant enumeration ([OWASP Multi-Tenant](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)). The same audit trail provides SOC 2 CC6.2 and CC6.3 evidence when every grant, change and revocation is its own event ([IntSignal](https://www.intsignal.com/signal/soc-2-user-access-review-evidence)). ASVS 8.1.1 requires written authorization rules, which GitLab keeps in sync by generating its docs from YAML with `rake gitlab:custom_roles:compile_docs` ([GitLab](https://docs.gitlab.com/development/permissions/custom_roles/)).

**Maker-checker.** Standard RBAC (ANSI/INCITS 359) only defines separation of duties at the role level. Static separation stops one user holding conflicting roles, and dynamic separation stops them activating both in one session ([Symas](https://www.symas.com/post/an-introduction-to-role-based-access-control-ansi-incits-359-2004)). Neither can express "the approver of *this* proposal is not its proposer". That rule is about an individual record, which is why Cedar expresses it as a `forbid` that overrides every `permit` ([Cedar](https://docs.cedarpolicy.com/auth/authorization.html)) and ReBAC expresses it as an exclusion. In a single-database app, the robust place for it is the domain transaction, which is where payhub's DB CHECK and `approvable_by?` already put it. Payhub also gets role-level separation for free, because each operator holds exactly one role and no role has both `proposals_create` and `proposals_decide`. That property should be asserted in a spec, not left implied.

## Verdict on the payhub plan (ui-design section 3)

### Keep

| Decision | Reason |
|---|---|
| Fixed roles in a frozen Ruby map, no permissions in the DB | Matches how every platform ships built-in roles, with Mastodon and GitLab as direct Rails precedents. Changes go through code review, deploy and git history, which is the change-management evidence auditors want. |
| Controllers check permissions (`authorize!(:x)`), never role names | This single choice makes custom roles and scoped API keys a data change later, with no edits at call sites (the GitHub and GitLab path). Add a lint or grep in `bin/check` that fails on `role ==` or `owner?` outside `Permissions` and the layer-4 assignment rules. |
| No Pundit, Action Policy or CanCanCan | With nine flat roles and record rules already in services, policy classes would only forward calls. The one feature worth having, a verify hook, is cheap to write (below). |
| Tenant scoping through `current_merchant` associations, 404 not 403 | This is the highest-value layer against the most common bug class, and the `/v1` controllers already do it. It avoids acts_as_tenant's default-scope conflict with operators. |
| Frontend reads `permissions[]` from `GET me` to hide UI only | Required by ASVS 8.3.1. Enforcement stays on the server. |
| `authorize!` writes a `denied` audit row | OWASP says to always log authorization failures. Include the role, the permission, the route, server-verified `merchant_id` and `request_id`, and never request bodies. |
| Maker-checker as a DB CHECK plus `approvable_by?` | Separation of duties per record is a domain invariant. Enforcing it in the database transaction cannot be bypassed and has no sync lag. |
| Layer-4 escalation rules (no self-role-change, admins assign up to Admin, one Owner) | These mirror Stripe's and GitHub's escalation controls and address the documented HackerOne-class role-assignment bugs ([HackerOne #605720](https://hackerone.com/reports/605720)). |
| Explicit permission lists for every role, no wildcards | Operator admin deliberately lacks `proposals_decide`. A wildcard would grant future permissions silently, as Azure's `*` does. |

### Change

| Change | Reason |
|---|---|
| **Name permissions `resource.verb` as strings (or symbols) with one delimiter, and split `payments_write` into `payments.capture`, `payments.cancel` and `payments.refund`.** Operator permissions get their own namespace (`ops.payments.poll`, `ops.proposals.decide`). | This matches GCP, Stripe and GitLab. An unambiguous delimiter makes names parseable for docs and grouping (`security_history_read` is not). Refund is the highest-risk verb (Stripe has a dedicated `refund_analyst`). The table can still group the three verbs under one row, but names become a public contract the moment restricted keys or custom roles exist, so split them now while it is free. |
| **Turn the map into a catalogue**: one `Permissions` file that declares each permission with a description and a `sensitive:` flag, plus the role-to-permission sets. At boot, raise if a role references an unknown permission, and make `authorize!` raise `ArgumentError` on an unknown name. | A typo becomes a crash rather than a silent 403 for everyone or a silent grant. The descriptions feed the generated docs and the TypeScript type. This is the in-Ruby equivalent of GitLab's YAML abilities. |
| **Add a fail-closed verification layer**: class-level declarations (`requires_permission :payments_refund, only: :create`, plus `allow_unauthorized` for sign-in and similar actions); an `after_action :verify_authorized` that raises in dev and test and logs an error in production; and a route-inventory spec that fails CI if any `Web::` action lacks a declaration. | Pundit's own docs say the after-action hook runs too late to be a failsafe. A before-action declaration enforces the check at runtime, and the route inventory is what actually makes "a new endpoint without a permission fails CI" true. |
| **Stop generating the matrix spec's expectations from the hashes.** Commit an independent expected matrix, for example `spec/fixtures/permission_matrix.yml`, or generate `docs/permissions.md` and fail CI when it is stale. Test every role with explicit `false` values, GitLab style. | A spec generated from the implementation is tautological. The committed matrix makes every grant change a reviewable diff, and the same file satisfies ASVS 8.1.1 and SOC 2 CC6.3. |
| **Generate `permissions.ts`** (a union type of permission names) from the catalogue during `bin/vite build` or a rake task. | A typo in a Vue permission check then fails `vue-tsc`. This closes the Ruby/TypeScript drift that caused Figma's incidents, at no cost. |
| **Add per-record `can_*` flags** (`can_capture`, `can_cancel`, `can_refund`) to payment and proposal detail payloads, computed on the server from the permission, the state machine and `approvable_by?`. | `permissions[]` cannot know a payment's state or who proposed something. Without flags, the UI shows buttons that return 409, and self-approval buttons appear. This is the hybrid GitHub-style pattern. |
| **Make role changes take effect immediately**: read the role from the database on each request, never cache permissions in the session, and have the client refetch `GET me` after any team or role change. | ASVS 8.3.2. The Omise report of a user who kept admin access after being downgraded is the failure this prevents ([HackerOne #1607756](https://hackerone.com/reports/1607756)). |
| **Add spec invariants for separation of duties**: no operator role has both `proposals_create` and `proposals_decide`; the approving transaction locks the proposal row (`lock!`) before checking state and approver; and a proposal whose payload changes after submission goes back to pending. | These make static and per-record separation of duties explicit, and close the race between two approvals and the edit-after-submit loophole. |
| **Write denial audit rows outside any surrounding transaction and add a simple threshold alert** (N denials per actor in a window). Leave the alert quiet for single denials. | A rolled-back transaction would silently drop the evidence. Stale-button denials are normal noise, and A01 asks for alerts on *repeated* failures. |
| **Cross-tenant request specs** across two merchants *and* a live/test twin pair, including jobs: pass `merchant_id` and re-scope inside the worker. | This checks the scoping that the twin-merchant model depends on. OWASP says to carry tenant context into async work and re-authorize there. |

### Do not adopt yet, and what would change that

| Deferred | Trigger that justifies it |
|---|---|
| **Custom roles (a DB `roles` table)** | Several paying merchants ask for a combination that no new *predefined* role can serve. Add a predefined role first, as GitHub and Stripe do. When the trigger fires, store built-in roles as immutable rows with stable IDs and make each custom role a base role plus added permissions (GitHub/GitLab), so it inherits new permissions and does not drift. |
| **Restricted `/v1` API keys** | A merchant asks for a key that cannot move money, or a key leak exposes the full blast radius. Reuse the same catalogue with Stripe-style per-resource None/Read/Write, where write implies read. |
| **Pundit or Action Policy** | Record-level rules start appearing in controllers rather than services, for example per-user ownership of resources, operators assigned to specific merchants, or field-level write rules (ASVS 8.2.3). Then Action Policy's scopes, failure reasons and matchers pay for themselves, and they can read the same catalogue. |
| **OPA, Cedar, Cerbos, SpiceDB or OpenFGA** | A second service or language must make the same decisions, sharing or hierarchical resources need "list what I can see", or policy must ship independently of app deploys. Choose a stateless engine if the attributes are available at request time, and a Zanzibar store only for a relationship graph. |
| **Postgres RLS** | A cross-tenant bug slips past the scoped finders, or a compliance requirement asks for database-enforced isolation. It needs `SET LOCAL`, a non-owner app role, an explicit operator policy, and tests run under the production role. |
| **acts_as_tenant or `default_scope`** | Not recommended even later. The operator side reads across merchants, and explicit association scoping plus the route and cross-tenant specs already cover what it would add. |
| **Rolify, CanCanCan, role hierarchies or `inherits_from`** | No trigger for Rolify or CanCanCan: one role per user in a CHECK-constrained column already covers role assignment. Consider hierarchies only if the role count roughly doubles and the lists become hard to review. Until then, explicit sets are easier to audit. |

## Conclusion

The research shifts the question from *which tool* to *which invariants the tool has to guarantee*. Every platform that scaled did so by making the permission name the unit of truth, and every serious failure described in the sources came from something other than the tool: logic drifting between two copies (Figma), a wildcard granting future access (Azure's fix), a role-assignment path that escalated (HackerOne), or a lookup that skipped the tenant. Payhub's plan already avoids the architectural traps. What it lacks are the mechanisms that stop those failures in *this* codebase: a declaration on every route that is checked in CI, an expected matrix that does not come from the code it tests, a TypeScript type generated from the Ruby catalogue, and permission names split finely enough that they will not need to be renamed once they are public.

The deferred items share one theme. Each becomes worthwhile when authorization data or decisions have to leave the single Rails process, whether to customers composing roles, to scoped API keys, to a second service, or to the database itself through RLS. Until then, the cheapest way to keep payhub's authorization scalable, maintainable and readable is a small catalogue that the code, the tests, the docs and the Vue app all read from, with a CI check that fails if any of them disagree.
