# PayHub UI: design

Status: draft for review, 2026-09-25.
Inputs: [use cases](2026-09-25-ui-use-cases.md) and `reports/Payment dashboard design standards.md`.

## 1. Architecture

**One Rails app, three Vite entrypoints, three URL spaces.**

| Area | Pages | JSON | Login | Vite entrypoint |
|---|---|---|---|---|
| Merchant | `/dashboard/*` | `/dashboard/api/*` | Merchant user session | `merchant.ts` |
| Operator | `/ops/*` | `/ops/api/*` | Operator session, separate cookie | `ops.ts` |
| Demo | `/demo/*` | `/demo/api/*` | None; test data of the demo merchant only | `demo.ts` |

- **Separate entrypoints, not one bundle.** Operator code is never shipped to a merchant's browser, and the demo bundle holds no login code. Shared components live in `app/frontend/shared/`.
- **The existing `/v1` API stays as it is.** It keeps `ActionController::API`, Bearer keys, Rack::Attack limits and its specs. The only change is key lookup moving to the `api_keys` table (section 2).
- **UI controllers inherit a new `Web::BaseController < ActionController::Base`.** It adds cookies, sessions, CSRF protection and one HTML shell action per area. Each JSON controller calls the **same services** as `/v1` (`CreateRefund`, `CapturePayment`, `CancelPayment`, `StuckPaymentSweeperJob.poll_now`), so the UI cannot do anything the domain refuses.
- **Cookies:** `_payhub_dashboard` scoped to `/dashboard`, `_payhub_ops` scoped to `/ops`, both `HttpOnly`, `Secure` in production, `SameSite=Strict`. A merchant session can never authenticate an operator request.
- **CSRF:** Rails puts the token in a meta tag. The shared HTTP client sends it as `X-CSRF-Token` on every write.
- **Idempotency on UI writes.** Money-moving POSTs (capture, cancel, refund, proposal approve) require an `Idempotency-Key` header and run through the existing `IdempotencyGuard`. The Vue modal creates one key when it opens and reuses it on every retry.
- **Logging:** lograge currently only formats `ActionController::API` requests. It will be extended to `Web::BaseController`, and poll endpoints will be marked so they skip request logging.

**Frontend stack (recommended):** Vue 3 + TypeScript, Vue Router, **TanStack Vue Query** for server state and polling, Tailwind CSS, **Reka UI** for accessible dialogs, menus and tables. No global store beyond the current-user query.

**Live updates:** polling through one composable, `useLiveQuery(key, fetcher, intervalFor)`. The interval is chosen from the data (for example the payment state) and polling pauses when the tab is hidden. Action Cable can replace this composable later without touching any page.

## 2. Data model

All new tables use UUID v7 keys and `structure.sql`, like the rest of the schema.

### Test mode: a twin merchant, not a column everywhere

Each merchant gets a **test twin**: a second `merchants` row with `livemode = false` and `live_merchant_id` pointing at the live one.

- `sk_test_…` keys authenticate as the twin and `sk_live_…` keys as the live merchant. Because every existing query is already scoped by `merchant_id`, test payments, ledger accounts, balances and events are **separated by the scoping that already exists**. Payments, refunds, captures and the ledger need no new column, and the chaos run and specs are unaffected.
- The dashboard's mode switch changes which of the two merchant ids the session reads from.
- Team members and API keys belong to the live merchant. Keys carry `livemode` to say which twin they open.
- This is the "separate environment" model that Adyen, Braintree and Square use, and that Stripe is moving toward with Sandboxes.
- **In this demo both modes route to the simulators.** Live mode is a separate data space, not real money. The UI says so.

## 3. Access control (RBAC)

**Yes, the UI needs role-based access control, and it stays deliberately small.** There are fixed roles, named permissions, a catalogue mapping one to the other, and a declared permission on every controller action. There are no custom roles, no policy gem, no permissions in the database, and no external policy engine. The research in `reports/RBAC implementation patterns.md` backs each of these choices and gives the trigger that would reverse it (see "Not adopted yet" below).

### Five layers, checked in this order

| Layer | Question it answers | Where it lives | Failure |
|---|---|---|---|
| 1. Authentication | Who are you? | Session cookie + 2FA | 401 |
| 2. **Tenant scoping** | Which merchant's data can you touch? | Every query starts from `current_merchant` (or its test twin) | 404, never 403, so other merchants' ids are not confirmed |
| 3. **Permission** | May your role do this kind of action? | `requires_permission` declaration, checked against `Permissions` | 403 |
| 4. Record rules | May this action happen to *this* record, by *you*? | Models and services | 409 / 422 |
| 5. Session conditions | Does this session allow it right now? | Step-up time, impersonation flag | 401 `step_up_required`, 403 `impersonation_read_only` |

Tenant scoping is the most important layer. Most real access bugs are one merchant reading another's data by guessing an id, not a role holding too much. The `/v1` controllers already scope through `current_merchant.payments.find`, and the UI controllers copy that pattern.

### Permission names: `resource.verb`

Permissions are strings of the form `resource.verb`, the same shape as Google Cloud, Stripe and GitLab. Operator permissions live under an `ops.` namespace so the two catalogues can never collide. **Controllers and views check permissions, never role names.** That one rule is what lets custom roles or restricted API keys arrive later as a data change, with no edits at call sites.

This keeps the four powers apart. **Developer** sees secrets but cannot move money. **Support** reverses money but sees no secrets and no balances. **Viewer** reads money but changes nothing. **Operator admin can grant access but cannot approve money movement.** No role holds both `ops.proposals.create` and `ops.proposals.decide`, and a spec asserts it.

Every role lists its permissions explicitly. There are **no wildcards**, because a wildcard silently grants permissions added later.

### The catalogue: one source for code, tests, docs and Vue

`app/lib/permissions.rb` declares every permission once, with a description and a `sensitive` flag, plus the role-to-permission sets for both areas.

```ruby
module Permissions
  CATALOGUE = {
    "payments.refund" => { description: "Refund a captured payment", sensitive: true },
    # ...
  }.freeze

  MERCHANT = {
    "support" => Set["payments.read", "payments.capture", "payments.cancel", "payments.refund"],
    # ...
  }.freeze
end
```

- **Fails at boot** if a role references a permission that is not in the catalogue.
- **Fails on typos.** Checking an unknown permission name raises `ArgumentError` instead of silently returning false for everyone.
- **Feeds everything else.** A rake task, `permissions:export`, writes two generated files, and CI fails when either is stale (`git diff --exit-code`):
  - `docs/permissions.md`: the readable matrix for reviewers and auditors (OWASP ASVS 8.1.1, SOC 2 access-review evidence).
  - `app/frontend/shared/permissions.ts`: a TypeScript union of permission names, so a typo in a Vue permission check fails `vue-tsc`. This stops the Ruby and TypeScript copies drifting apart, the failure that caused incidents at Figma.

### Fail closed: every action declares its permission

A controller concern gives each `Web::` controller a class-level declaration that runs **before** the action:

```ruby
class Dashboard::Api::RefundsController < Dashboard::Api::BaseController
  requires_permission "payments.refund", only: :create
end

class Dashboard::Api::SessionsController < Dashboard::Api::BaseController
  allow_unauthorized only: %i[create]   # explicit, greppable opt-out
end
```

- The check runs as a `before_action`, so a denied request has no side effects.
- An `after_action` verification raises in development and test if an action ran without a declaration or an opt-out. In production it logs an error and increments a metric. It is a development aid, not the safeguard.
- **The actual safeguard is a route-inventory spec.** It lists every route handled by a `Web::` controller and fails CI if any action has neither `requires_permission` nor `allow_unauthorized`. This is what makes "a new endpoint without a permission fails CI" true.
- A `bin/check` grep fails on role-name checks (`role ==`, `owner?`, `admin?`) outside `Permissions` and the layer-4 role-assignment rules.
- Authorization is declared **before** the idempotency `around_action`, so a denial never opens a transaction.

### What the Vue app receives

- **`GET me` returns `permissions[]`.** It is used for navigation and page-level visibility only.
- **Record payloads carry `can` flags.** A payment detail includes `can: { capture:, cancel:, refund: }` and a proposal includes `can: { approve:, reject: }`. The server computes them from the permission, the state machine and `approvable_by?`. Only the server knows that *this* payment is `unknown`, or that *you* proposed *this* change, so without these flags the UI would show buttons that return 409.
- **The Vue app never enforces anything** (ASVS 8.3.1). The server re-checks every request.
- **Role changes take effect immediately** (ASVS 8.3.2). The principal and its role are loaded from the database on every request, and permissions are never cached in the session. After any team or role change the client refetches `GET me`.

### Rules that roles alone cannot express (layer 4)

- **Nobody approves their own proposal.** This is enforced by a database CHECK and by `OperatorProposal#approvable_by?`.
- **Approval locks the proposal row** (`lock!`) before checking its state and approver, so two approvers cannot both act on it.
- **A proposal's payload is immutable after submission.** To change it, the proposer withdraws it and submits a new one, so an approver always approves exactly what they read.
- **Nobody changes their own role or removes themselves.**
- **Admins assign roles up to Admin only.** Only the Owner creates another Owner, through ownership transfer. A merchant always has exactly one Owner, enforced by a partial unique index.
- **Payment actions follow the state machine.** Support holding `payments.refund` still cannot refund an `unknown` payment.

### Denials are audited and watched

- Every 403 from layer 3 writes an `audit_events` row with result `denied`. The row holds the actor, role, permission, route, server-verified `merchant_id` and `request_id`, and never request bodies, tokens or session ids (OWASP Logging Cheat Sheet).
- Because the check runs before any transaction opens, a rollback can never drop the denial row.
- A Prometheus counter, `authz_denied_total{area, permission}`, backs one alert: many denials from one actor in a short window. A single denial is normal (a stale button) and alerts nobody.
- 404s from tenant scoping are counted separately. A burst of them from one actor suggests someone is enumerating ids.

### Not adopted yet, and what would change that

| Deferred | Trigger |
|---|---|
| Custom roles (a `roles` table) | Several merchants need a combination no new *predefined* role covers. Then built-in roles become immutable rows, and each custom role is a base role plus added permissions, so it inherits new permissions. |
| Restricted `/v1` API keys | A merchant asks for a key that cannot move money. Reuse this catalogue with per-resource none/read/write. |
| Pundit or Action Policy | Record-level rules start appearing in controllers instead of services. Either gem can read this same catalogue. |
| OPA, Cedar, SpiceDB, OpenFGA | A second service or language needs the same decisions, or sharing features need "list everything I can see". |
| Postgres row-level security | A cross-tenant bug slips past scoped queries, or a compliance requirement asks for database-enforced isolation. |
| acts_as_tenant, `default_scope`, Rolify, CanCanCan | Not planned. Operators read across merchants, and one role per user in a CHECK-constrained column already covers role storage. |

**Applying an approved proposal** runs in one transaction. A payment transition calls `Payment#transition!` with `source: "operator"`, and its metadata carries the proposal id, both operator ids and the reason. A ledger correction posts a balanced transfer through `Ledger`, linked to the original transfer and tagged `source: operator`. If the payment has moved since the proposal was made, applying fails and the proposal is marked failed. It is never forced.

## 5. Email

- Re-enable `action_mailer/railtie`. Mailers: `InvitationMailer`, `SecurityMailer` (new-device sign-in, 2FA disabled, ownership transferred), `OperatorMailer` (proposal waiting for approval).
- All mail goes through `deliver_later` on Sidekiq.
- docker compose gains a `mailcatcher` service. SMTP is on port 1025, and the inbox is at `localhost:1080`.
- Production SMTP settings come from environment variables and are outside this plan's scope.

## 6. Errors and edge cases

- **One error shape.** UI endpoints reuse `ApiError` and its JSON shape, so the Vue client has a single error handler.
- **401** sends the browser to that area's sign-in page and keeps the intended path. **403** shows a "your role can't do this" message; buttons for disallowed actions are not rendered at all.
- **409 and 422 from idempotency or the state machine** show the server's message and refetch the payment. A state change that another user or the sweeper made first is expected here, not an error to hide.
- **Step-up expired:** the endpoint returns 401 with code `step_up_required`. The client opens the step-up modal and retries once with the same idempotency key.
- **Lockout:** returns 423 with the unlock time. Success and failure look the same for an unknown email, so emails can't be enumerated.
- **Impersonation expiry:** after 30 minutes the next request returns 403 with code `impersonation_expired`, and the banner disappears.

## 7. Testing

- **Request specs for every UI endpoint.**
- **Authorization matrix spec.** Its expected values come from a hand-reviewed file, `spec/fixtures/permission_matrix.yml`, **not** from `Permissions`, so the spec can actually disagree with the code. Every role is listed for every permission, with explicit `false` values (GitLab's convention). Any grant change shows up as a readable diff in review.
- **Route-inventory spec.** It fails if any `Web::` action lacks `requires_permission` or `allow_unauthorized`.
- **Separation-of-duties spec.** It fails if any operator role holds both `ops.proposals.create` and `ops.proposals.decide`.
- **Cross-tenant specs.** They use two merchants *and* a live merchant with its test twin, and cover background jobs, which receive a `merchant_id` and re-scope inside the worker.
- **Generated files are checked.** `permissions:export` runs in `bin/check`, and CI fails if `docs/permissions.md` or `permissions.ts` changed.
- **Model specs** for the database rules: one owner per merchant, no self-approval, proposal row locking and immutable payloads, append-only `audit_events` and `psp_calls`.
- **Mailer specs** assert on `ActionMailer::Base.deliveries`.
- **Vitest** for composables: the poll interval, the idempotency key lifecycle, and the error handler.
- **Playwright** for three end-to-end flows: sign in with 2FA then refund; operator proposes and a second operator approves; demo `timeout_then_webhook` reaching `captured`.
- **`bin/check` gains** `vue-tsc`, `eslint`, `vitest` and `bin/vite build`. CI installs Node. The existing chaos run and deterministic simulation must stay green after the `api_keys` and twin-merchant migrations.

## 9. Pieces for the user to write

These are small, judgment-heavy pieces. The surrounding code will be scaffolded with a TODO at each spot.

1. **`pollIntervalFor(state)`** in the Vue composable: which states stop polling, and how fast `unknown` polls compared with `pending`.
2. **`spec/fixtures/permission_matrix.yml`**: the intended access boundary, written by hand as the independent truth the catalogue is tested against. The catalogue is scaffolded from section 3; you decide whether that table is really what each role should do.
3. **`OperatorProposal#approvable_by?(operator)`**: the maker-checker guard.
4. **The `PspCall` redaction rules**: which request and response fields are removed before a row is written.
